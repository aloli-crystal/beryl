= Installation FreeBSD par pkgbase — architecture
:toc: left
:toclevels: 3
:sectnums:
:icons: font
:source-highlighter: rouge

[.lead]
Document de design pour l'installation de FreeBSD 15 *via pkgbase*
(`pkg install FreeBSD-*`) en alternative durable aux tarballs
`base.txz` / `kernel.txz`. Branche `feat/pkgbase-install`.

== Pourquoi

L'installation actuelle pose les *distribution sets* (`base.txz` +
`kernel.txz`) via `bsdinstall` (préambule `installerconfig`, cf.
ADR-013). C'est le chemin officiel et testé de FreeBSD 15.0, mais :

* *Pas pérenne.* FreeBSD pousse `pkgbase` : le système de base devient
  un jeu de paquets `pkg` (`FreeBSD-runtime`, `FreeBSD-kernel-generic`,
  …). Les mises à jour deviennent `pkg upgrade` au lieu de
  `freebsd-update` ; granularité par composant ; cohérence avec les
  paquets applicatifs.
* *Mise à jour bancale en tarball.* `freebsd-update` est binaire,
  monolithique, et mal adapté à un parc reconstruit-jetable.

Objectif : pouvoir poser un host avec `freebsd.install_type: packages`
et obtenir un FreeBSD 15 fonctionnel, *à parité* avec le chemin
tarball, validé en QEMU.

== État des lieux (ce qui existe déjà)

[cols="2,3", options="header"]
|===
| Élément | État

| Champ `freebsd.install_type`
| Lu par `cli/bootstrap.cr` (`distribution_sets` \| `packages`),
  validé (`VALID_INSTALL_TYPES`).

| `templates/install-pkgbase.sh`
| Script d'install pkgbase *complet et autonome* : GPT (EFI + swap +
  ZFS), pool ZFS + datasets, bootstrap `pkg`, `pkg install FreeBSD-*`,
  `loader.conf`/`fstab`/`rc.conf`, clés SSH root, durcissement sshd,
  bootloader EFI, export du pool. Placeholders `__TARGET_DISK__`,
  `__POOL_NAME__`, `__HOSTNAME__`, `__ABI__`, `__SWAP_GB__`,
  `__TIMEZONE__`, `__AUTHORIZED_KEYS_B64__`.

| `bootstrap/installer.cr` (`Installer`)
| Rend + téléverse + exécute `install-pkgbase.sh`, reboot, attend le
  SSH. **MAIS** rattaché au flux *déprécié* mfsBSD-on-disk
  (ADR-010/011), hors du chemin principal.

| `bootstrap/qemu_in_rescue.cr` (`QemuInRescue`)
| Flux *actuel* (mfsBSD-in-QEMU côté rescue, ADR-012/013). Fait
  l'install *tarball via bsdinstall*. **Refuse** `install_type:
  packages` (`PkgbaseNotYetImplemented`, gate l.256).
|===

Autrement dit : la *logique* pkgbase est écrite, mais branchée sur le
mauvais (ancien) moteur. Il faut la router à travers `QemuInRescue`.

== Cible

`install_type: packages` doit emprunter `QemuInRescue` (le moteur
actuel) mais, *à l'intérieur du mfsBSD lancé en QEMU*, exécuter un
install **pkgbase direct** (gpart/zfs/pkg) au lieu de
`bsdinstall` + tarballs.

[source,text]
----
rescue Linux → QEMU → mfsBSD
   ├── install_type: distribution_sets  → bsdinstall + base.txz/kernel.txz   (existant)
   └── install_type: packages           → install-pkgbase.sh (gpart/zfs/pkg)  (à câbler)
----

Le script pkgbase ne dépend pas de `bsdinstall` (donc pas du problème
Capsicum d'ADR-013) : il pilote `/mnt` directement, comme le post-install
no-chroot d'ADR-013.

== Écart de parité à combler

`install-pkgbase.sh` est aujourd'hui *minimal* (1 disque, root seul).
Le chemin tarball (`rescue-run-vm.sh`) couvre bien plus. À aligner :

[cols="2,3,1", options="header"]
|===
| Capacité | Tarball (actuel) | pkgbase

| Multi-disque / RAID (mirror, raidz…)
| Oui (`--raid`, `zpool create mirror …`)
| *Manque* (mono-disque figé)

| Users + clés + sudoers
| Oui (`pw -R /mnt`, sudoers.d)
| *Manque* (root seul)

| Packages applicatifs (`sudo`, `zsh`…)
| Oui (`pkg -r /mnt install`)
| *Manque* (uniquement FreeBSD-base)

| Pools de données (`data_pools`)
| Oui (`DataPoolSpec`)
| *Manque*

| Chiffrement (ZFS natif / GELI + Tang)
| Oui (couplage crystal-clevis-zfs)
| *Manque* (gros morceau, cf. zpool-encryption-architecture.adoc)

| ABI / version (`FreeBSD:15:amd64`, `base_release_0`)
| N/A (mfsBSD SE embarque les dists)
| À fiabiliser (détection arch + URL repo pkgbase)
|===

NOTE: La partie *post-install commune* (users, packages, sudoers) est
déjà extraite côté no-chroot ADR-013. Idéalement, pkgbase et tarball
*partagent* cette phase post-base : seule la pose du **base system**
diffère (tarballs vs `pkg install FreeBSD-*`). C'est l'axe de
factorisation à viser plutôt que de dupliquer `install-pkgbase.sh`.

== Plan d'implémentation (phasé)

. *Phase 1 — câblage minimal (mono-disque, root)* +
  Lever le gate `PkgbaseNotYetImplemented` ; router `install_type:
  packages` dans `QemuInRescue` vers un driver pkgbase qui rend +
  exécute `install-pkgbase.sh` dans la VM mfsBSD. Valider en QEMU un
  boot FreeBSD 15 pkgbase mono-disque, root SSH OK.

. *Phase 2 — parité base* +
  Factoriser la phase post-base (users/sudoers/packages/timezone)
  commune tarball↔pkgbase ; brancher pkgbase dessus. Multi-disque /
  RAID. Pools de données.

. *Phase 3 — chiffrement* +
  Réintégrer le couplage `crystal-clevis-zfs` (ZFS natif + Tang) sur le
  chemin pkgbase (cf. zpool-encryption-architecture.adoc).

. *Phase 4 — bascule défaut (plus tard)* +
  Une fois pkgbase validé sur ≥ 2 serveurs Aloli réels, envisager d'en
  faire le défaut (`install_type` par défaut → `packages`). Décision
  séparée, non dans cette branche.

== Validation

* *QEMU obligatoire* (règle Aloli) : étendre le banc
  `prod-crystal/qemu/` avec un scénario d'install pkgbase bout-en-bout
  (boot disque → SSH root → `uname -r` == 15.x → `pkg info | grep
  FreeBSD-runtime`). Idéalement un `qemu/test-pkgbase.sh` jumeau de
  `test-apply.sh`.
* *Specs unitaires* sur le rendu du script (placeholders, ABI,
  escaping) — réutiliser/adapter ceux d'`Installer`.

== Vérifications (sources officielles, juin 2026)

[cols="2,3", options="header"]
|===
| Question | Réponse vérifiée

| URL du repo pkgbase
| *Confirmé.* Pour 15.0-RELEASE :
  `pkg+https://pkg.freebsd.org/${ABI}/base_release_0`
  (`base_release_<VERSION_MINOR>`, donc `_0` pour 15.0). Host
  `pkg.freebsd.org`. Bootstrap :
  `.../base_release_0/FreeBSD-pkg-bootstrap-15.0.pkg`.

| Signature / fingerprints
| *BUG confirmé dans `install-pkgbase.sh`.* Le script met
  `fingerprints: "/usr/share/keys/pkg"` ; la bonne valeur est
  `/usr/share/keys/pkgbase-${VERSION_MAJOR}` → `/usr/share/keys/pkgbase-15`
  (clés `trusted/awskms-15`, `trusted/backup-signing-15`). À corriger
  en Phase 1.

| `base_release_0` vs `base_latest`
| `base_release_0` = figé sur 15.0-RELEASE (install reproductible, ce
  qu'on veut). `base_latest` est plus complet (variants kernel) mais
  suit l'amont. `FreeBSD-kernel-generic` est présent dans
  `base_release_0` — suffisant pour une install standard.

| ABI / arch
| Dériver `FreeBSD:15:$(uname -p)` de la *cible*. pkgbase 15.0 publie
  amd64 *et* arm64 → *le banc QEMU local (arm64) peut valider Phase 1*,
  même si les dédiés Aloli sont amd64. NB : `Installer#abi` a un défaut
  obsolète `FreeBSD:14:amd64` à passer à 15.

| `pkg -c` (chroot) vs `--rootdir`
| *À valider in vivo.* La communauté installe le base avec
  `pkg -c /mnt …` (chroot), et `install-pkgbase.sh` fait pareil. MAIS
  ADR-013 a montré que pkg dans un chroot incomplet meurt en `SIGSYS`
  (Capsicum, `/dev/urandom` absent). Donc soit *monter devfs dans /mnt*
  avant `pkg -c`, soit basculer sur `pkg --rootdir /mnt` (no-chroot,
  cohérent ADR-013). Choix tranché par le test QEMU de Phase 1.
|===

== Questions encore ouvertes

. *Réécrire vs réutiliser.* Garder `install-pkgbase.sh` autonome
  (simple) ou le fondre dans le driver `rescue-run-vm.sh` (factorisation
  post-base) ? Recommandation : factoriser la phase post-base, garder la
  pose du base system distincte par `install_type`.
. *Histoire de mise à jour.* Acter `pkg upgrade` du base comme voie de
  MAJ pkgbase (vs `freebsd-update` en tarball) — impacte la recette
  `freebsd-updates` côté apply.
. *Statut d'`Installer` (legacy).* Le code de rendu pkgbase vit dans la
  classe dépréciée `Installer`. Le déplacer/partager proprement vers le
  chemin `QemuInRescue` plutôt que ressusciter `Installer`.
. *Présence des clés fingerprints dans mfsBSD SE 15.* Les clés
  `/usr/share/keys/pkgbase-15/` doivent exister dans l'environnement
  mfsBSD au moment de l'install (sinon les fetcher) — à vérifier en
  Phase 1.
