= Dépôt de paquets privé (poudriere) — Spécification
:toc: left
:icons: font
:status: SPÉCIFICATION — à reprendre semaine du 15 juin 2026 (trop tôt pour coder)

[abstract]
Cadrage d'un dépôt `pkg` privé, signé, construit par poudriere, pour
servir les paquets *manquants* (ou retirés) du dépôt FreeBSD officiel à la
flotte de serveurs gérée par beryl. Ce document ne décrit PAS une
implémentation : il fixe les objectifs, l'architecture, les choix de
sécurité et les décisions à trancher avant de démarrer.

== 1. Contexte et déclencheur

beryl installe aujourd'hui les outils non packagés (ex. `chruby`) via la
primitive `make-install` : `fetch` d'un tarball upstream + `make install`
sur *chaque* serveur de prod. C'est un pis-aller :

* `make install` exécute un Makefile (capacité plus large que `pkg`) ;
* le tarball n'est pas signé (confiance dans l'URL + HTTPS uniquement) ;
* un compilateur / `make` doivent être présents sur la prod ;
* on subit l'upstream : **`chruby` a purement disparu des ports FreeBSD**,
  alors qu'il restait installé sur d'anciens serveurs.

Ce dernier point est l'argument central : sans dépôt maîtrisé, la
disponibilité d'un paquet n'est pas sous notre contrôle.

== 2. Objectifs

. **Un seul mécanisme** : tout s'installe par `pkg install`, y compris nos
  paquets maison → fin de `make-install` sur la prod.
. **Build centralisé** : compilation *une fois* sur un builder dédié, pas
  sur chaque serveur. Aucun toolchain de build sur la prod (surface
  d'attaque réduite).
. **Intégrité** : paquets **signés**, vérifiés par `pkg` à l'installation.
. **Maîtrise des versions** : on décide ce qui est disponible et quand il
  change → immunité aux retraits / sauts de version surprise de l'upstream.
. **Reproductibilité** : un paquet identique déployé partout.

NON-objectif (pour l'instant) : remplacer l'intégralité du dépôt officiel
(cf. modèle B, plus bas).

== 3. Architecture cible

[source]
----
                         (overlay git : ports maison)
                                   |
   ┌─────────────────┐   poudriere bulk   ┌──────────────────────┐
   │  BUILDER FreeBSD │ ─────────────────▶ │  dépôt pkg signé      │
   │  (jails propres) │                    │  (répertoire + meta)  │
   └─────────────────┘                    └──────────┬───────────┘
        ports officiel                                │ nginx (mesh privé)
        + overlay maison                              ▼
                                       ┌──────────────────────────┐
                                       │  serveurs de prod         │
                                       │  pkg install chruby …     │
                                       │  (FreeBSD-base + ce dépôt)│
                                       └──────────────────────────┘
----

=== 3.1 Le builder

* Un hôte **FreeBSD** dédié au build (poudriere construit dans des jails
  propres et jetables). Peut être une jail sur un serveur existant ou une
  petite box dédiée.
* **Alignement ABI impératif** : le builder doit produire pour la *même*
  version que les cibles — FreeBSD **15.0 amd64** (nos serveurs pkgbase).
  La jail poudriere = `15.0-RELEASE` amd64.
* Arbre des ports officiel + **overlay maison** (`poudriere -O`) contenant
  nos ports (ex. `chruby` : on récupère le Makefile/distinfo/pkg-plist
  depuis l'historique git des ports, on les fige dans l'overlay).

=== 3.2 Signature

* poudriere signe le dépôt avec une **clé RSA** (`PKG_REPO_SIGNING_KEY`).
* Les serveurs vérifient via `fingerprints` (clé publique distribuée).
* La **clé privée de signature ne quitte jamais le builder**. Sa gestion
  (stockage, sauvegarde, rotation) est un point de sécurité à part entière.

=== 3.3 Service du dépôt

* Le dépôt est un répertoire
  (`/usr/local/poudriere/data/packages/<jail>-<ports>/`) servi en **HTTP(S)**.
* **Reco sécurité** : servir sur le **mesh privé** (headscale/tailscale —
  cf. recettes `headscale-*`), pas en public. Les serveurs tirent le dépôt
  via l'interface `tailscale0`. Pas d'exposition publique du dépôt.

=== 3.4 Côté serveurs (clients)

* Coexistence avec **pkgbase** : la base vient de `FreeBSD-base`, les ports
  de *ce* dépôt (modèle B) ou de ce dépôt **+** l'officiel (modèle A).
* Config : `/usr/local/etc/pkg/repos/aloli.conf` :
+
[source]
----
aloli: {
  url: "https://repo.mesh.aloli/${ABI}",
  mirror_type: "srv",
  signature_type: "fingerprints",
  fingerprints: "/usr/local/etc/pkg/fingerprints/aloli",
  enabled: yes,
  priority: 100          # > 0 pour primer l'officiel si même paquet
}
----

== 4. Deux modèles

[cols="1,3,3"]
|===
| | **A — Compléments** | **B — Dépôt complet**

| Contenu | Seulement les manquants (chruby, …) | Tout ce qu'on utilise
| En plus de l'officiel | Oui | Non (le remplace)
| Effort de build | Minime | Important (build de tout)
| Reproductibilité | Partielle | Totale
| Risque ABI | Faible drift possible si un complément dépend d'une lib officielle qui bouge | Nul (tout cohérent)
| Immunité retraits | Pour nos paquets | Totale
|===

**Reco** : démarrer en **A** (résout chruby immédiatement, effort minimal,
paquets autonomes type pur-shell = zéro risque), garder **B** comme cible
si le besoin de reproductibilité totale se confirme.

== 5. Sécurité (synthèse)

* Paquets **signés** + vérifiés à l'install (vs tarball non signé actuel).
* **Aucun toolchain de build sur la prod** (le build est sur le builder).
* Dépôt servi **sur le mesh privé**, pas en public.
* Clé de signature **confinée au builder** ; politique de sauvegarde +
  rotation à définir.
* L'overlay de ports est **versionné (git)** → tout changement de recette
  de build est auditable.

== 6. Intégration beryl

beryl reste pertinent et se *simplifie* :

. Nouvelle primitive **`pkg-repo`** : pose `/usr/local/etc/pkg/repos/<nom>.conf`
  + la clé publique dans `fingerprints/`. Idempotente.
. Recette **`pkg-repo-aloli`** : enrôle un serveur sur notre dépôt.
. Les recettes applicatives **basculent vers `pkg-install`** : `chruby`
  redevient `pkg-install: { packages: [chruby] }`. **`make-install` peut
  être retirée** (ou conservée en secours rarissime).
. Option : recettes pour **bootstrapper le builder** lui-même (installer +
  configurer poudriere, l'overlay, la clé) — beryl gère alors aussi
  l'infra de build.

== 7. Phasage proposé

[cols="1,4"]
|===
| Phase | Contenu

| 0 | *(état actuel)* `make-install` pour chruby — fonctionne, on garde.
| 1 | Monter le builder poudriere (jail 15.0), overlay avec `chruby`, clé de
      signature, build, servir sur le mesh.
| 2 | beryl : primitive `pkg-repo` + recette d'enrôlement ; bascule `chruby`
      → `pkg-install` ; retrait de `make-install`.
| 3 | Étendre l'overlay aux autres manquants ; évaluer le passage modèle B.
| 4 | Pipeline de rebuild (MAJ FreeBSD / avis de sécurité) + supervision.
|===

== 8. Décisions à trancher (semaine prochaine)

. **Emplacement du builder** : jail sur un serveur existant (lequel ? capacité
  disque/CPU pour les builds) vs box dédiée.
. **Modèle A ou B** au démarrage (reco : A).
. **Gestion de la clé de signature** : génération, stockage, sauvegarde,
  rotation. Réutilise-t-on le coffre `beryl env` (`.env.toml.age`) ?
. **Service du dépôt** : sur le mesh headscale (URL, certif TLS interne) — quel
  hôte porte nginx ? Le builder lui-même ?
. **Overlay de ports** : nouveau dépôt git `aloli-ports` ? Convention de suivi
  des Makefiles récupérés de l'historique des ports officiels.
. **Cadence de rebuild** et déclencheurs (cron, avis de sécurité FreeBSD).
. **Interaction pkgbase** : confirmer la coexistence `FreeBSD-base` + ce dépôt
  (priorités, ABI `15.0`), et si modèle B, qui fournit alors *aussi* les ports
  courants (postgresql, nginx, ruby-install…) → tout passe par poudriere.
